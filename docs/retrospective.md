# 회고록

## 2026-11-11 — 독립 포크 제품명·버전 정리

### 잘된 점

- 원본 릴리스의 기능 상당수가 이미 포크에 구현되어 있음을 소스로 확인하고, 버전 숫자만으로 업데이트 필요성을 판단하지 않았다.
- 표시명 변경이 Electron 프로필 경로와 설치 스크립트·외부 브릿지에 미치는 영향을 함께 확인했다. 기존 데이터 경로와 실행 명령을 유지하도록 명시했다.
- 비공식 포크 표시와 원본 출처를 남기고, 업데이트 확인 대상을 포크로 바꿔 독립 버전 관리 방향과 맞췄다.

### 아쉬운 점과 검증 한계

- 첫 설정 스키마 검증 명령은 설치되지 않은 @develar/schema-utils를 사용해 실패했다. 설치된 Ajv와 electron-builder 스키마로 다시 검증해 통과했다.
- 임시 프로필에서 앱 표시·버전·경로 재정의만 실행 확인했다. 실제 기존 프로필을 사용하는 업그레이드와 각 OS 설치 패키지·Android는 검증하지 않았다.

### 다음 작업에 적용할 점

- 제품명 변경 시 표시 문자열 외에 데이터 경로·실행 파일명·설치 파일명·업데이트 출처를 함께 점검한다.
- 독립 포크 버전과 원본 버전을 구분해서 기록하고, 기존 동기화 형식에 영향을 주는 변경은 데스크톱·Android 호환성을 함께 확인한다.
- 배포 검증 시 빌드 성공, 설치·실행, 기존 데이터 호환성, 터미널 기능 검증을 구분한다.

## 2026-11-05 — RHEL·bash·zsh 매뉴얼

### 잘된 점

- 기억 대신 공식 이미지에서 측정했다. RHEL 9.8의 OpenSSH가 흔히 알려진 8.7이 아니라 9.9p1임을 찾아, 메이저 버전만으로 단정하지 않고 측정한 이미지 버전을 문서에 적었다.
- 문서의 주장을 시험으로 돌려 `sshd -T`가 `without-password`로 표시하는 점을 찾아 반영했다. 작성만 했다면 놓쳤을 내용이다.
- `TMOUT` 시험에서 bash·zsh에는 경고가 없음을 확인해, 유휴 방지 명령의 경고 감지가 ksh 전용이라는 점을 문서에 남겼다.
- `ID_LIKE`의 실제 값을 확인해 RHEL 자체와 호환 배포판을 함께 맞추는 규칙을 만들었다.

### 아쉬운 점

- 처음에 사용자에게 묻지 않고 Docker Desktop을 켰다. 사용자는 podman을 쓰라고 했고, 켠 것을 다시 꺼야 했다. PC의 앱을 실행하기 전에 쓰는 환경부터 물었어야 했다.
- 스크린샷의 주소를 읽어 서버를 추측해 물었는데, 실제 대상은 `homelab/soyo`였다.
- Red Hat 문서를 직접 읽지 못해 검색 결과에 의존했다. 공식 문서로 표시한 링크도 스크립트로는 확인하지 못했다.
- `script`가 없는 환경을 고려하지 않아 첫 `TMOUT` 시험이 무효였다. 시험이 실패했을 때 문서 문제인지 시험 문제인지 구분하는 데 한 번 더 돌려야 했다.
- 시스템을 바꾸는 RHEL 명령은 끝내 실행하지 못했다. 다음에는 일회용 VM 같은 환경이 필요하다.

### 다음 작업에 적용할 점

- 버전 문서에는 측정한 대상과 날짜를 함께 적는다.
- 사용자 PC의 프로그램이나 서비스를 켜기 전에 어떤 환경을 쓸지 확인한다.
- 다른 사람의 서버에서 시험할 때는 무엇을 남기고 무엇을 지웠는지 기록한다.
- 매뉴얼의 시스템 변경 명령은 일회용 RHEL VM에서 확인하기 전까지 검증 완료로 기록하지 않는다.

## 2026-11-05 — 서버별 설정, 스니펫 동기화, 접속 로그

### 잘된 점

- 스니펫 동기화에서 이전 버전을 실제로 빌드해 업데이트 경로를 시험했다. 지문 형식이 바뀌면 모든 다중 기기 사용자에게 거짓 충돌이 나는 문제를 설계 단계에서 짚었고, 기존 e2e로는 확인되지 않는 경로를 직접 확인했다.
- 유휴 방지 명령은 잘못 보내면 파일이나 다른 프로그램에 글자가 들어가므로, 판단을 순수 모듈로 분리해 단위 테스트했다. 이 테스트가 `$` 앞에 공백이 있는 프롬프트를 놓치는 정규식 버그를 잡았다.
- 접속 로그는 라이브러리 소스를 읽는 데 그치지 않고 실제 서버에 접속해 비밀번호와 입력이 로그에 없는 것을 시험으로 고정했다.
- `THIRD_PARTY_NOTICES.txt`처럼 환경 때문에 생긴 차이를 작업과 구분해 커밋에서 뺐다.

### 아쉬운 점

- 프롬프트 규칙을 사용자의 실제 프롬프트를 보기 전에 일반적인 모양으로 만들었다. 사용자가 `viewer@eaiap01t [/eai/viewer] `를 알려 주지 않았다면 간격 전송이 동작하지 않는 채로 끝났을 것이다. 요청의 대상 서버가 분명하면 프롬프트부터 물어봐야 했다.
- `postgres@db:~$ ` 같은 계정 프롬프트를 DB 프롬프트로 잘못 제외하는 규칙도 처음에 넣었다. 금지 목록은 넓게 쓰기 쉬우니 반대 사례를 같이 시험해야 한다.
- AIX 의 `unset TMOUT` 문제는 처음에 readonly 가 유력하다고 답했는데 사용자 확인으로 틀렸다. 원인을 끝내 밝히지 못하고 우회 기능을 만들었다.
- Android 는 이 PC 에서 빌드할 수 없는데도 코드를 넣어, 컴파일되지 않은 변경이 main 에 들어갔다. 다음 Android 빌드에서 먼저 확인해야 한다.
- 처음 만든 스니펫 e2e에 패널 여는 방법을 추측해 쓴 코드가 있어 실패했다. 코드를 먼저 읽었으면 한 번에 끝났다.
- 여러 세션이 같은 작업 트리에서 일해 기능이 한 커밋에 섞였다. 기능별로 나누기 어려워 되돌리기와 추적이 불편해졌다.

### 다음 작업에 적용할 점

- 저장 형식을 바꿀 때는 이전 버전에서 올라오는 경로와 이전 버전이 끼어드는 경로를 함께 시험한다.
- 입력을 대신 보내는 기능은 보내도 되는 조건을 좁게 잡고, 실제 사용 환경의 값(프롬프트 등)을 시험에 넣는다.
- 원인을 모르는 채 우회한 것은 우회라고 기록하고, 해결로 적지 않는다.
- 같은 작업 트리를 여러 세션이 쓸 때는 기능을 끝낼 때마다 커밋한다.
- 이번에 남은 실제 AIX, SSH 끊김, Android 빌드 검증을 완료로 기록하지 않는다.

## 2026-11-03 — ARM64 패키징과 PRoot 실행

### 잘된 점

- Electron의 `--arm64` 지정 외에 실제 터미널 기능을 담당하는 네이티브 모듈을 확인했다. Linux prebuild가 없는 `node-pty`를 별도로 빌드해 x64 바이너리가 ARM64 패키지에 남는 문제를 처리했다.
- 임시 빌드 폴더를 사용해 호스트 개발용 모듈을 보존했고, 기존 x64 빌드와 PTY 실행으로 회귀 여부를 확인했다.
- deb 메타데이터뿐 아니라 아카이브 내부 바이너리까지 검사해 실제 배포 파일의 아키텍처를 확인했다.
- 사용자 장비의 커널 문자열로 PRoot 환경임을 파악하고, `--no-sandbox` 실행 결과로 진단 범위를 좁혔다.

### 아쉬운 점

- 빌드·아키텍처 검증만으로 ARM64 실사용 가능 여부를 확인할 수 없었다. 실제 장비에서의 기본 실행은 PRoot 샌드박스 제약으로 실패했다.
- 검증에 사용한 설치 의존성과 저장소의 Electron 선언 버전이 달랐다. 재현 가능한 릴리스 검증에는 lockfile을 사용한 clean install 결과를 따로 남겨야 한다.
- ARM64 앱 실행 성공 이후 PTY·SSH·시리얼 기능은 확인하지 못했다. 창이 열리는 것과 기능 검증 완료를 구분해야 한다.

### 다음 작업에 적용할 점

- 시작 오류를 진단할 때 배포판·CPU뿐 아니라 실제 커널과 PRoot·컨테이너 여부를 함께 확인한다.
- 빌드 완료, 네이티브 모듈 검사, 앱 시작, 핵심 기능 확인을 각각 기록한다.
- 샌드박스 우회는 필요한 사용자 환경의 명시적 옵션으로 안내한다. 단일 환경의 호환 문제를 이유로 전체 배포의 샌드박스를 해제하지 않는다.
- 릴리스 전 clean install과 실제 ARM64 장비의 PTY·SSH·시리얼 검증을 수행한다. 이번 작업에서 완료한 검증으로 기록하지 않는다.

## 2026-11-11 — 포워딩과 재접속 상태를 실제 동작과 연결하기

- 포워딩 설정이 존재하는 것과 리스너 할당, 목적지 TCP 접속, 서비스 인증 성공은 서로 다른 상태다. 표시와 도움말에서 확인 범위를 구분하고, 점검용 연결을 사용자 통계에서 제외했다.
- 여러 터미널이 같은 포워딩을 공유하므로 최초 생성 터미널보다 포워딩의 수명이 길어질 수 있다. 공유 풀과 마지막 사용자 해제 기준을 두고, 최초 터미널 종료 후에도 연결이 유지되는 것을 테스트했다.
- 프롬프트 인식을 단독 `>`까지 넓히면 이어쓰기 입력에 자동 명령을 보낼 수 있다. 기존 제외 규칙을 유지하고, 사용자가 실제 프롬프트 예시와 줄바꿈을 지정하도록 했다. 기본 예시는 최종 요청한 대괄호 경로 형식으로 맞췄다.
- TMOUT은 별도 명령 채널의 환경값과 현재 터미널 셸의 값이 다를 수 있어 실제 셸에서 조회했다. 값을 읽지 못한 경우를 0이나 미설정으로 단정하지 않고 안내한다.
- 재접속 규칙은 앱·서버 UI에서 같은 편집기를 사용하고, 실제 예약 계산도 공통 함수로 묶었다. 설정 화면 검증 중 편집기가 잘못된 설정 탭에 들어간 것을 발견해 연결 탭으로 옮기고 앱 테스트를 다시 통과시켰다.
- 로컬 TCP와 모의 SSH 클라이언트 테스트는 상태 전이와 수명·통계를 검증하지만 실제 SSH 정책이나 서버 셸 차이까지 보장하지 않는다. 실제 서버와 다른 OS·패키지 검증은 별도로 남겼다.
